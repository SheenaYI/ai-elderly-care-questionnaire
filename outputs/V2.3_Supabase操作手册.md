# 智能养老问卷 V2.3 Supabase 更新操作手册

> 2026-11-02 补充：本手册的 0005 基础迁移仍适用，但本次修订还需要审查 `supabase/migrations/0006_v23_weight_mode.sql`。请同时阅读 [2026-11-02 更新与操作说明](2026-11-02_更新与Supabase操作说明.md)，不要只执行0005就部署新版页面。所有SQL均尚未由本次任务执行。

适用人：保管现有 Supabase 项目账号的队友，以及负责 Netlify 发布的同学。

本手册对应2026-11-02最新代码。GitHub推送可触发Netlify部署，但不会自动更新Supabase；本次未执行正式数据库操作。请先由负责人审查并确认本手册和 SQL，再由队友操作。代码更新与数据库更新是两件事，真实链路验收完成前不可正式发放。

## 1 本次为什么需要数据库更新

旧项目是 V1.1：一份合并问卷，每人 6 道 DCE，4 个配置各 12 个评分，理解检查题号 Q6/Q7；还必须回答额外的理想配置题。

V2.3 是两份独立问卷：老人版没有 DCE，而有三档偏好与 6 道授权实验；照护者每人 4 道 DCE；两卷均为两个配置各 8 个评分，并增加 100 分分配、注意力题和新的背景信息。

旧表的必填身份字段、非空 DCE 分卷、12 个非空评分列不能直接表示新版老人答卷。为避免将缺失分数填成 0 或更改旧表含义，本次只新增一张主表和几个视图，不删除或修改旧表。

| 新对象 | 作用 |
| --- | --- |
| `survey_v23_submissions` | 每份已提交答卷一行；含版本、类型、渠道、分卷、时间，以及完整的结构化原始 JSON |
| `submit_survey_v23(jsonb)` | 仅服务端能执行的原子提交函数；检查资格、数量、权重、任务配置，处理重复提交 |
| `survey_v23_dce` | 展开 DCE 任务、原始方案 A/B、实际左右位置和最终选择 |
| `survey_v23_ratings` | 每个配置、每个评分项一行，保留题项表述版本 |
| `survey_v23_answers` | 展开小写题号的常规答案和首次理解检查记录 |
| `questionnaire_versions` 的 `V2.3` 行 | 登记新版，默认 `is_active=false`，未经团队验收不开放收集 |

自主授权、权重、三档偏好、随机计划和完整配置快照均完整保存在主表 `payload`，后台提供相应的结构化 CSV。旧 `participants` 等表和 `submit_survey` 函数、历史数据、登录账号与原有白名单均保留。

## 2 操作前先核对真实项目

先确认打开的是现有正式 Supabase 项目，记下项目名称和 Project URL。不要新建项目来替代原项目。

先导出历史答卷和现有数据库结构作为备份。可使用团队已有的备份方式，或先从 Table Editor 导出各旧表 CSV。账号密码、service_role key 不要放入 GitHub、前端或共享截图。

在 SQL Editor 新建查询，先运行以下只读检查。保存结果供团队核对。

```sql
-- PostgreSQL 必须支持 security_invoker 视图（15或以上）。
select current_setting('server_version') as postgres_version;

-- 必要的旧对象是否存在。
select to_regclass('public.questionnaire_versions') as versions,
       to_regclass('public.research_admins') as admins,
       to_regprocedure('public.is_research_admin()') as admin_check,
       to_regprocedure('public.submit_survey(jsonb)') as legacy_submit;

-- 查看旧表字段，和仓库的0001至0004迁移核对。
select table_name,column_name,data_type,is_nullable
from information_schema.columns
where table_schema='public'
  and table_name in ('participants','dce_choices','profile_ratings',
                    'comprehension_checks','survey_responses','custom_config_choices')
order by table_name,ordinal_position;

-- 查看现有RLS是否开启。
select c.relname,c.relrowsecurity
from pg_class c join pg_namespace n on n.oid=c.relnamespace
where n.nspname='public' and c.relkind='r'
order by c.relname;

-- 查看现有策略。
select tablename,policyname,roles,cmd,qual,with_check
from pg_policies where schemaname='public'
order by tablename,policyname;

-- 保留旧版本计数，迁移后再次核对。
select questionnaire_version,submission_status,count(*)
from public.participants
group by questionnaire_version,submission_status;
```

如果必要对象不存在，或真实 RLS 与仓库描述不一致，先停止，不要通过重新执行旧初始化脚本来“修复”。把不一致的检查结果交给负责人确认。

仓库中的安全设计是：匿名用户没有研究表读写权限；登录用户只有在 `research_admins` 白名单中才可读取；写入经 Netlify 函数使用服务端 key 完成。不得为了调通问卷新增“所有人可读写”策略。

## 3 负责人确认后才执行迁移

本次完整 SQL 的交付副本为 `outputs/0005_survey_v23.sql`，代码中的权威来源为 `supabase/migrations/0005_survey_v23.sql`。两者内容一致。

负责人确认的事项：新增上述对象、复用现有管理员白名单、V2.3 与历史表分开存放、新版默认停用、未提交草稿不上传。数据库不会自动删除任何历史数据；本次也不会改写旧 RPC 或旧策略。

确认后，队友在 SQL Editor 中粘贴完整 SQL，整份执行。不要只执行其中一段。SQL 包含事务，发生错误会整体回滚；不要删除出错行后跳过继续。

已有数据库依次执行 0005、0006，不要重跑 0001–0004。若0005已经执行，只补0006；不要在0006之后重跑0005，否则旧函数定义会覆盖新校验。全新测试数据库先按旧说明完成 `supabase/schema.sql`，再依次执行0005、0006。

0006权威文件为 `supabase/migrations/0006_v23_weight_mode.sql`：只把老人排序校验改为“仅排序模式必填，100分模式可不填排序”。不新增或删除表、不覆盖答卷、不改变RLS或函数执行权限。函数定义与预期不同时会中止，不能跳过报错。执行后可用以下只读查询核对条件已更新：

```sql
select position($check$if (w->>'mode'='ranking_only' or jsonb_array_length(w->'ranking') > 0)$check$
  in pg_get_functiondef('public.submit_survey_v23(jsonb)'::regprocedure)) > 0 as weight_mode_updated;
-- 应为true。false时不要正式发放。
```

0005不会把已启用的V2.3改回停用，也不会删除答卷；0006可重复运行。必须按顺序应用，勿自行编辑迁移后覆盖既有定义。

## 5 Netlify 代码和环境变量

沿用当前 Netlify、GitHub、Supabase 架构。没有新增必需环境变量。

| 环境变量 | 用途与核对 |
| --- | --- |
| `VITE_SUPABASE_URL` | 现有 Supabase 项目 URL；前端公开配置 |
| `VITE_SUPABASE_ANON_KEY` | 现有公开 anon key，不能换成 service_role |
| `SUPABASE_URL` | 服务端项目 URL |
| `SUPABASE_SERVICE_ROLE_KEY` | 只给服务端 Functions 使用，不加 `VITE_` 前缀 |
| `VITE_SUBMIT_ENDPOINT` | 保持 `/api/submit-survey` |
| `VITE_ALLOW_DEMO_MODE` | 正式发布设为 `false`，避免将本地演示当作收集 |
| `VITE_QUESTIONNAIRE_VERSION` | 可更新为 `V2.3` 便于团队查看；新版实际版本固定由代码常量管理，不允许环境变量改变研究版本 |

构建命令、输出目录、函数目录沿用 `netlify.toml`：`npm run build`、`dist`、`netlify/functions`。现有 `/api/submit-survey` 和 `/api/admin/export` 的转发规则无需新增。

先让负责代码的同学将本次修改提交到团队约定的分支，并在 Netlify 创建预览部署。不要在数据库迁移尚未确认时将新页面开放正式发放。网页本地 `npm run dev` 只运行 Vite，不会启动 Netlify Functions；因此本机演示完成不等于云端已经保存。

## 6 使用测试渠道验收真实链路

先经负责人批准临时启用 V2.3（这条 SQL 是单独的操作，不会被 0005 自动执行）：

```sql
update public.questionnaire_versions set is_active=true where id='V2.3';
```

在预览部署里使用以下入口，所有测试答卷明确标记为 `sample_channel=test`：

- `/questionnaire/elder?channel=test`
- `/questionnaire/caregiver?channel=test`

不要用不带参数的正式入口提交虚构答案。测试时完成一次老人版、一份照护者 A 卷和一份照护者 B 卷；A/B 是随机的，新建答卷才重新分配。刷新、返回、重新打开同一入口不会改变同一草稿的分卷与展示位置。

验证清单：

1. 老人版有三道三档偏好、六道固定顺序授权情景：C4自行→C4子女同意→C7自行→C7子女同意→C8自行→C8子女同意，以及两个配置各8项评分。问卷共6步，提交前检查不计步；照护者共5步。
2. 照护者 b0 选“否”会终止；只有实际照护者能继续。
3. A 卷恰好 T01/T02/T07/T08；B 卷恰好 T04/T05/T06/T10。后台查看任务编号，参与者页面不显示配置编码。
4. 两次刷新分卷、题序、左右位置、两个评价配置不变。
5. 100分题填99分不能提交；老人默认只显示分数框且无需排序。切换“仅排序”才显示三个排序栏，三项分数在数据中保持null；切回100分时清除排序。分别验证两种模式写入成功，不能只验证照护者。
6. 理解检查首次答错后修改，后台首次错误仍然保留；注意力题不通过会保留原答并标记，不自动删除。
7. 页面只有收到 `ok=true` 且 `mode=supabase` 的服务端成功回执才显示云端保存成功。
8. 网络失败保留草稿；同一编号同样答案的网络重试不重复插入；已提交答卷不能覆盖成另一份答案。
9. 登录原有研究员账号，在 V2.3 区域切换到“功能测试”渠道，看到刚才的答卷；默认“正式”渠道不应计入它们。
10. 检查各项 CSV：配置评分每份答卷16行，照护者 DCE 选择4行，DCE 长表8行且每题恰好一个 `chosen=1`，老人授权6行。
11. 退出研究员账号后无法读取数据或导出；非白名单账号也不得访问。

数据库只读核对：

```sql
select survey_version,sample_channel,respondent_type,split_version,count(*)
from public.survey_v23_submissions
group by survey_version,sample_channel,respondent_type,split_version;

select participant_id,count(*) from public.survey_v23_dce
where sample_channel='test' group by participant_id;
-- 照护者每份4行。

select participant_id,count(*) from public.survey_v23_ratings
where sample_channel='test' group by participant_id;
-- 每份16行。
```

测试数据保留为test，不必删除。后台默认筛选正式渠道和instrument_revision=2026-11-02。旧答卷没有修订标识，按legacy解释，不能与本次修订直接混析。b4新第3/4项为“与伴侣居住/和其他家庭成员居住”，旧数据仍是“轮流居住/住在养老机构”；CSV的answer_label按修订还原，原始序号保留。

```sql
select coalesce(payload->>'instrument_revision','legacy') as instrument_revision,
       sample_channel,respondent_type,count(*)
from public.survey_v23_submissions
group by 1,2,3;
```

所有CSV附instrument_revision。正式分析须同时筛选版本、修订、样本渠道与受访者类型。新旧草稿使用不同本机存储键，不自动搬迁或删除旧草稿。

## 7 正式发布与暂停

上述真实链路验收全部通过后，再正式发布代码并发放两个不带 `channel=test` 的独立入口。V2.3 的题目与任务来源在 `src/features/surveyV23/content.ts`，不要只修改某个页面文字而漏改字典。


这只暂停提交，不删除记录。不要删除表或恢复旧数据库备份来“回滚”。若要恢复旧网页代码，请先考虑旧问卷是否还应接受新数据，避免版本切换期间收集错误版本。
