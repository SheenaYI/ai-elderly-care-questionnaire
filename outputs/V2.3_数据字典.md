# 智能养老问卷 V2.3 数据字典

本字典对应 `src/features/surveyV23/content.ts`、`model.ts`、`validation.ts` 与新版后台导出。V1.0/V1.1 仍使用原有表和旧字典，不得与 V2.3 合并解释。

## 答卷与版本字段

| 字段 | 取值与含义 |
| --- | --- |
| participant_id | 匿名 UUID，一份答卷唯一标识；老人/照护者独立生成 |
| survey_version | 固定 V2.3；与 A/B 分卷不同 |
| instrument_revision | 本次为2026-11-02，存于payload；缺失为legacy。所有CSV附此列，不与问卷版本或分卷混用 |
| respondent_type | elder=老人本人；caregiver=实际家庭照护者 |
| sample_channel | formal=正式；pilot=预测试；test=功能测试；默认正式 |
| split_version | 照护者随机 A/B；老人为 null，不得填 A 或 0 |
| started_at | 客户端开始时间，ISO UTC |
| submitted_at（表列） | 数据库确认接收时间，服务端生成 |
| payload.submitted_at | 客户端提交时间，ISO UTC；与上列分别保留 |
| consent / consent_at | 是否同意与同意时间；必须在作答开始后、提交前 |
| eligible | 自述符合对应人群资格；服务端还独立校验照护者 b0 |
| care_years | 选择 b3“偶尔帮忙”时填写的年限；不适用时为 null |
| configuration_snapshot | 本版 C1–C8 与 x1/x2/x3 的完整快照，防止只存展示文本 |
| step / updated_at | 本机当前步骤与最近更新时间；不作为 question_id |
| simulation_events | 配置、关联任务、事件类型、距开始时间的毫秒数及停留时间 |

未提交草稿仅保存在浏览器localStorage，新键为 `aiecq:V2.3:2026-11-02:{respondent_type}:{sample_channel}`。旧V2.3键及 `aiecq:draft:v1` 不自动读取、升级或删除。没有服务端草稿分母，因此不能据此计算全体访问者退出率。

## 常规题号和选项编码

所有 `question_id` 使用小写。常规单选在 `answers` 中保存从 0 开始的选项索引；总体意愿和注意力题保存 1–5 的量表分数。不要混用这两种编码。

| question_id | 题义 | 选项编码 |
| --- | --- | --- |
| a1 | 年龄 | 0=60–65；1=66–70；2=71–75；3=76及以上 |
| a2 | 居住 | 0=一个人住；1=和老伴一起住；2=和子女一起住；3=和其他家庭成员一起住 |
| a3 | 智能设备使用 | 0=完全不会用；1=会一点（打电话、微信）；2=用得很熟练 |
| a4 | 身体情况 | 0=完全能自己照顾自己；1=偶尔需要人帮忙；2=经常需要人照顾 |
| a5 | 跌倒/突发疾病风险 | 0=几乎没有；1=有一点；2=比较大；3=很大 |
| a6 | 最近一年跌倒 | 0=没有；1=1次；2=2次及以上 |
| a7 | 简单提示理解检查 | 0=只能看到正常/疑似跌倒提示（正确）；1=完整视频；2=什么都看不到 |
| a8 | 异常详细记录理解检查 | 0=平时什么都不管；1=平时基础判断、异常才详细记录（正确）；2=只在白天 |
| a9 | 总体采纳意愿 | 1=很不愿意；2=不太愿意；3=说不好；4=比较愿意；5=非常愿意 |
| a10 | 最担忧的事，最多2项 | 字符串数组："0"=出事发现不了；"1"=私事被看到；"2"=自己说了不算；"3"=乱报警/出故障；"4"=其他 |
| a11 | 100分分配 | answers记录 scores/ranking_only 模式；实际分数与排序在 weight_allocation |
| a-check | 注意力核对 | 同a9的1–5；按题目要求选择2才通过；不通过仍保存原答 |
| a12 | 理想设备开放反馈 | 文本，可空或不出现 |
| b0 | 是否实际照护60岁以上家中老人 | 0=是；1=否（终止，不得提交） |
| b1 | 照护者年龄 | 0=18–29；1=30–44；2=45–59；3=60及以上 |
| b2 | 与老人关系 | 0=子女；1=配偶；2=其他亲属；3=其他家庭成员 |
| b3 | 照护频率/年限 | 0=每天且超过1年；1=每天但不足1年；2=每周数次；3=偶尔帮忙，并填care_years |
| b4 | 老人居住状态 | 本次修订：0=独居；1=与您同住；2=与伴侣居住；3=和其他家庭成员居住。legacy旧答卷的2/3仍分别表示轮流居住/住在养老机构，CSV answer_label按修订还原 |
| b5 | 老人健康/跌倒风险 | 0=无；1=轻微；2=中度；3=较高；完整选项见content.ts |
| b6 | AI养老设备了解程度 | 0=使用过；1=了解未使用；2=不了解 |
| b7 | 摘要信息理解检查 | 0=仅简要提示（正确）；1=完整视频；2=不能传递信息 |
| b8 | 异常详细监测理解检查 | 0=平时完全不检测；1=基础持续、异常详细监测（正确）；2=仅白天 |
| b9 | 总体采纳意愿 | 1=非常不同意；2=不同意；3=一般；4=同意；5=非常同意 |
| b10 | 最担忧的事，最多2项 | 字符串数组："0"=安全识别不足；"1"=隐私暴露；"2"=自主权受限；"3"=误报/故障；"4"=其他 |
| b11 | 100分分配 | 仅scores模式；分数在weight_allocation |
| b-check | 注意力核对 | 同b9的1–5；2为通过；不通过仍保存 |
| b12 | 安全/隐私/自主平衡开放题 | 文本，可空或不出现 |

`a-check/b-check` 是定稿 `a-Check/b-Check` 的统一小写形式，不占用 a1–a12/b0–b12 中既有题义。

理解检查单独保存在 `comprehension`：`question_id`、`first_answer`（0起）、`first_correct`、`final_answer`、`retry_count`。必须最终理解后继续，但首次错误不覆盖。CSV 的 answer 是最终选择，首次字段独立保留。

## 实验属性与配置

X1=接收者能看多细；X2=谁能接收；X3=何时详细采集，三者独立。所有方案的基础异常识别与紧急报警能力相同。

| 配置 | x1 | x2 | x3 |
| --- | --- | --- | --- |
| C1 | 0 | 0 | 0 |
| C2 | 0 | 0 | 1 |
| C3 | 0 | 1 | 1 |
| C4 | 1 | 0 | 0 |
| C5 | 1 | 0 | 1 |
| C6 | 0 | 1 | 0 |
| C7 | 1 | 1 | 0 |
| C8 | 1 | 1 | 1 |

标准描述由附录C的三个分句按 X1→X2→X3 展示。配置编号用于后台与数据，正式问卷不向参与者显示配置编码。

## 照护者DCE

| split_version | task_id | 原始方案A配置 | 原始方案B配置 |
| --- | --- | --- | --- |
| A | T01 | C1 | C3 |
| A | T02 | C5 | C6 |
| A | T07 | C3 | C5 |
| A | T08 | C3 | C7 |
| B | T04 | C2 | C4 |
| B | T05 | C2 | C6 |
| B | T06 | C2 | C8 |
| B | T10 | C3 | C4 |

每份照护者答卷4题；题序和左右位置随机。随机计划一次生成并持久化，服务端用 participant_id 和版本确定性复核计划。

- `dce_plan`：题号、展示次序（1起）、原始方案A/B配置、实际左右配置。
- `dce_choices`：上述字段加 selected_side（left/right）、selected_configuration_id、response_duration_ms。
- `scheme_a_configuration_id` 与 `scheme_b_configuration_id` 始终指任务表原始方案，不是屏幕左/右。
- 原始配置属性还可由 configuration_snapshot 还原；CSV长表直接附x1/x2/x3。
- `v23_long` 每题2行，alternative_position表示屏幕位置，canonical_scheme表示原任务A/B，chosen为0/1。每题恰好一个chosen=1。
- 此版保持二选一，不增加opt-out；Pilot备选任务没有被擅自启用。

## 老人三档偏好与授权

`elder_preferences.X1/X2/X3` 的合法值只有 0/50/100，分别表示少、都行/看情况、多。不得将50拆分归入两端，也不把这些编码当作DCE属性系数。

`autonomy_plan` 和 `autonomy_choices` 包含 configuration_id（C4/C7/C8）、attribute_id（X1/X2/X3）、authorization_condition（self/children）、display_order、scenario_id。choice为：

- willing：愿意。
- unwilling：不愿意。
- indifferent：都可以（没有影响），必须单列。

情景配置按C4=100、C7=110、C8=111递进。2026-11-02修订固定为C4自行/子女同意→C7自行/子女同意→C8自行/子女同意；legacy为六题整体随机。配对依据configuration_id与authorization_condition，不依据页面序号；顺序设计不同须分修订分析。

## 两个配置的感知评价

`rating_plan` 从C1–C8随机抽2个不重复配置并固定评价顺序。`profile_ratings` 每配置包含 configuration_id、rating_order（1/2）、wording_version（老人colloquial，照护者standard）和8个scores。

item_id统一小写 s1/s2/p1/p2/a1/a2/i1/i2。它们是**配置评分项编号**，不是常规题的question_id。比如背景题a1与自主感评分item_id=a1处在不同模块与列，不能混用。

| 评分项 | 老人版原文 | 照护者版原文 |
| --- | --- | --- |
| s1 | 我觉得这台设备能及时发现家里可能出的危险。 | 我认为该系统能够及时发现老人可能发生的安全风险。 |
| s2 | 我觉得真出事的时候，这台设备能帮上忙。 | 我认为该系统在紧急情况下能提供有效的安全保障。 |
| p1 | 我担心这台设备收集的信息太多。 | 我担心该系统收集了过多的老人个人信息。 |
| p2 | 我担心不该看的人能看到我在家的详细情况。 | 我担心不必要的人员能够查看老人的详细活动信息。 |
| a1 | 用了这台设备，我平时想怎么过日子还是怎么过。 | 我认为老人使用该系统后，仍能自主安排日常生活。 |
| a2 | 我觉得这台设备不会管得太多、让我不自在。 | 我认为该系统不会过度干预老人的私人生活。 |
| i1 | 要是真能装，我愿意用这台设备。 | 如果该系统实际可用，我愿意选择或为老人配置它。 |
| i2 | 我愿意长期用这台设备。 | 我愿意在实际养老照护中长期使用该系统。 |

全部为1–5分：1=完全不同意，5=完全同意。p1/p2高分表示更强隐私担忧，禁止反向改成隐私满意度。未答不能填0。每份答卷导出感知评价长表16行，各配置分开。

## 100分与排序

`weight_allocation.mode` 为scores或ranking_only。

scores模式的security/privacy/autonomy必须为0–100整数、均非空、合计100。合法的0分与未答null不同。

ranking_only仅限老人确实无法打分时使用。ranking保存按重要性从高到低的三个不同项目；三项分数全部为null，不纳入分数均值。本次scores模式只显示分数框，ranking为空数组；不根据分数推算排序。legacy老人分数模式可能含完整排序，原样保留。

## 导出与分析筛选

后台默认统计V2.3正式渠道、2026-11-02修订。全部CSV含participant_id、survey_version、instrument_revision、respondent_type、sample_channel、split_version、submitted_at。以下可分开导出：

| 数据集 | 行单位 |
| --- | --- |
| v23_raw | 每份答卷1行；payload为可解析JSON，保留完整随机计划、快照和原答 |
| v23_answers | 常规问题或理解检查1行；含首次答案字段 |
| v23_dce | 每个DCE任务1行 |
| v23_long | 每个DCE任务的一个实际展示备选项1行 |
| v23_ratings | 某配置的某item评分1行 |
| v23_autonomy | 某授权情景1行 |
| v23_preferences | 每位老人1行，3个三档值 |
| v23_weights | 每份答卷1行，含权重/排序、校验结果、注意力答案与通过标记 |

CSV为UTF-8 BOM，并处理Excel公式注入。数组与对象按JSON保存，不会转成`[object Object]`。分析前先按版本、样本渠道、人群筛选；对于attention_passed=false的处理由研究团队按预先确定的规则决定，系统不擅自删除。
