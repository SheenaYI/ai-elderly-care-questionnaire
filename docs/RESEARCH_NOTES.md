## B. 需要研究团队确认的问题

### B1【重要】6 道"同向变化"题存在完全支配关系，可能退化为无信息选择

文件中被标为"同向变化"的 6 题，其两个方案在**全部三个属性上**形成同向的暴露差异，
即其中一个方案在 X1、X2、X3 上全部更低（或全部更高）。程序化检查结果：

| 题号 | 卷别 | 配对 | 低暴露方案 | 高暴露方案 | 关系 |
|---|---|---|---|---|---|
| T01 | A | C1 → C3 | C1 (0,0,0) | C3 (0,1,1) | C1 在 X2、X3 上均更低 |
| T02 | A | C1 → C5 | C1 (0,0,0) | C5 (1,0,1) | C1 在 X1、X3 上均更低 |
| T03 | A | C1 → C7 | C1 (0,0,0) | C7 (1,1,0) | C1 在 X1、X2 上均更低 |
| T06 | B | C2 → C8 | C2 (0,0,1) | C8 (1,1,1) | C2 在 X1、X2 上均更低 |
| T10 | B | C4 → C8 | C4 (1,0,0) | C8 (1,1,1) | C4 在 X2、X3 上均更低 |
| T12 | B | C6 → C8 | C6 (0,1,0) | C8 (1,1,1) | C6 在 X1、X3 上均更低 |

**为什么这可能构成问题。** V1.0 在统一前提中已明确告诉参与者：
"所有方案基础报警性能相同"。在这一前提下，更高的暴露水平（详细数据可被查看、
更多人可查看、全天持续详细记录）**不带来任何被陈述的安全收益**，只有成本。
因此在这 6 题中，一个理性且已理解提示的参与者有很强动机选择低暴露方案。

**后果。** 这 6 题的选择几乎可由"低暴露方案"单一规则预测，贡献的属性层面信息有限；
并且会人为推高 X1、X2、X3 三个系数估计中的负向部分（因为 X1/X2/X3 从 0 升到 1
在低暴露方案中总是被打包在一起）。

V1.0 第五部分已经预见到这一风险，原文为：
"同向变化题是否太容易？…若多题接近单边选择且贡献信息有限，应在保留可识别性和
平衡性的前提下，优先改为更多反向权衡配对；修改后必须重新检查矩阵，不能只替换单题。"

**本项目的处理方式（未擅自改动设计）。** 按用户指令，网站**严格实现 V1.0 的
C1–C8 与 T01–T12 原始配对**，不做任何替换。同时：

1. 本项记录在此，供 Pilot 阶段核查。
2. 管理后台提供逐题选择分布统计，Pilot 时可直接观察 6 道同向题是否出现单边选择。
3. 问卷数据结构支持将来整体替换任务表（`dceTasks.ts` 单文件），
   替换后 `npm test` 会自动重新校验矩阵秩与平衡性。

**建议（待确认，不擅自实施）。** Pilot 中若确认这 6 题呈单边选择，可考虑将部分
同向题改为反向权衡配对（X3 提高安全感的潜在正向作用因此才可被识别），
替换后必须重新校验每卷秩 = 3 与属性平衡。

## D. 本项目的实现决策（供研究团队复核）

以下不是研究设计的改动，而是"文件未规定、但实现必须做出选择"的地方。
逐条列出，便于研究团队确认或要求调整。

### D1 模块四"4 个配置的平衡分配"具体机制

**文件规定**（V1.0 模块四）："每位参与者从 C1–C8 中按预设平衡规则获得 4 个不同配置，
评价任务顺序随机。"文件**未**规定具体算法。

**实现机制**（`src/lib/randomization/index.ts` 的 `buildRatingPlan`）：
把 C1–C8 视为长度 8 的循环序列，对第 k 位参与者取起点偏移 `o = k mod 8`，
以步长 2 连续取 4 项（步长 2 与 8 互质，保证 4 项互不相同）：

```
评价配置 = [ S[o], S[o+2], S[o+4], S[o+6] ]
```

**性质（已由自动化测试验证）**：
- 每人恰好 4 个**不同**配置；
- 连续 8 位参与者恰好使每个配置被评价 4 次 → **完全均衡、无随机漂移**；
- 可复现、可审计：给定序号即可推出配置集合，同时草稿中显式保存 `rating_plan`。

**偏移量 o 的来源**（重要，请研究团队确认）：
`o = hashString("seq:" + participant_id) mod 8`，其中 `participant_id` 为随机 UUID。

- 该做法保证**批次层面**的均衡（UUID 随机 ⇒ 8 个桶近似均匀）；
- 但**不保证**"前 8 位参与者恰好逐轮均衡"。已由测试给出实测分布：
  800 位模拟参与者下，各配置被评价次数与理论期望的偏差 < 15%。

**替代方案（本项目未采用，若需严格执行请告知）**：
由服务端在收到提交时按**到达顺序**分配 `sequence_index` 并下发给前端。
这能严格保证逐轮均衡，但需要服务端在问卷开始时可写数据库，
从而在未配置 Supabase 时无法完成分配（会阻断 Demo 模式的问卷填写）。
当前实现选择"前端自足"，以保证未配置后端时问卷依然可完整填写。

**为什么必须处理这件事**：若所有参与者的偏移量都固定为 0，
则**每个人都会评价同一组 4 个配置**，其余 4 个配置在总体样本中得不到任何评分，
直接影响"结果表二（属性对感知的影响）"的可估计性。实现中已避免该缺陷。

## E. 新增模块六「理想配置自由设定」（V1.0 之外的设计变更）

**状态：已实现，待研究团队确认。**

本节记录一处**在 V1.0 之外新增的研究内容**。按本文档开头的原则，任何设计变更
都应由研究团队确认；因此这里如实记录：改了什么、为什么、对分析意味着什么、
以及怎么撤回。

### E1 改了什么

在 V1.0 五个模块之后、提交前检查之前，新增一个步骤（问卷流程第 6 步）：

| 项目 | 内容 |
|---|---|
| 位置 | 总体评价（模块五）之后、提交前检查之前 |
| 形式 | 三个**独立的系统设置开关**（`role="switch"`），分别对应 X1 / X2 / X3 |
| 内容 | 让参与者主动拼出"自己最愿意长期使用的一套配置" |
| 是否必填 | **必填**。三个开关状态都已明确才算完成（默认全关 = C1） |
| 记录 | 三个水平 + 匹配到的配置编码（C1–C8）+ 作答耗时 |

三个开关与 DCE 属性完全对应，因此共有 2×2×2 = 8 种组合，
**恰好与 C1–C8 一一对应**，`matched_profile_id` 字段记录反查结果。

### E2 为什么要加

V1.0 的 DCE 只能测出"在两两对比中被迫取舍"的结果——参与者常常需要
在安全与隐私之间牺牲一边。但它**测不到**"如果不受任何约束，人们真正想要什么"。

新增本模块后，可以对比两个量：

- **DCE 选择**：受约束下的显示性偏好（revealed trade-off）
- **自由设定**：不受约束的理想配置（stated ideal）

两者之间的差距本身就是一个有意义的分析对象：例如"在 DCE 中不得不接受
仅摘要信息的人，自选时是否仍然选择仅摘要"，可用来讨论权衡中的被迫程度。

### E3 对分析的影响（请研究团队注意）

1. **不改变 DCE 的任何设计**。C1–C8、T01–T12、A/B 分卷、平衡分配均未改动。
2. **是独立变量，不是 DCE 的一部分**。分析时应作为单独的结果变量处理，
   不要把它与 `dce_choices` 混在一起做条件 Logit。
3. **可能受顺序/疲劳影响**。它排在问卷最后，参与者此时已见过 4 个配置的评价与
   DCE 的 6 组对比，可能产生锚定或学习效应。建议在 Pilot 中检查该部分
   与 DCE 选择的一致性，并在论文中说明其位置。
4. **隐私担忧方向不变**。该部分只记录配置选择，不涉及量表计分方向。

### E4 数据结构

新增一张表 `custom_config_choices`（每人一条）：

| 列 | 类型 | 说明 |
|---|---|---|
| `participant_id` | text, unique, FK | 关联参与者 |
| `x1` / `x2` / `x3` | smallint, 0/1 | 三个开关状态 |
| `matched_profile_id` | text, `^C[1-8]$`, 可空 | 反查得到的配置编码 |
| `response_duration_ms` | integer, ≥0 | 该部分耗时 |
| `created_at` | timestamptz | 写入时间 |

- RLS 与其余研究数据表一致：仅白名单管理员可读，写入只经 `submit_survey()`。
- 导出：新增 `custom_config` 数据集；`merged` 宽表新增 5 列
  （`custom_x1`/`custom_x2`/`custom_x3`/`custom_matched_profile_id`/
  `custom_response_duration_ms`），便于与 DCE 选择直接对比。
- 后台新增"理想配置分布"面板，展示各配置被自由选择的次数与
  "开启开关数量"的分布。

### E5 怎么撤回

若研究团队决定不加这一部分，撤回步骤：

1. `src/features/questionnaire/steps.ts`：从 `STEP_ORDER` 移除 `'ideal'`，
   把 `TOTAL_PROGRESS_STEPS` 改回 6，删除 `STEP_META.ideal`，后续步骤 index 减 1。
2. `src/pages/QuestionnairePage.tsx`：删除 `ideal` 分支，`overall` 的 onContinue 改回 `'review'`。
3. `src/lib/validation/schemas.ts`：从 `submissionSchema` 移除 `customConfig`，
   删除 `checkCompletion` 中的对应项。
4. 数据库：保留 `custom_config_choices` 表即可（不再写入，不影响其他数据），
   或另写迁移删除。
5. **升级 `QUESTIONNAIRE_VERSION`**（例如 V1.1 → V1.2），以便区分数据版本。

## F. 关于"是否更换数据收集方式"的结论

研究团队曾提出"有没有比 Supabase 更简便的收集方式（例如直接导出 CSV）"。
记录结论如下，避免重复讨论。

**结论：保留 Supabase。** 理由：

| 方案 | 能否满足本研究 | 判定 |
|---|---|---|
| Supabase（当前） | 能：服务端校验 + 匿名写库 + 导出 + 管理后台 | ✅ 采用 |
| 前端直接下载 CSV | **不能**：数据只在参与者本机，收不回来（除非让参与者自己发邮件） | ❌ |
| 第三方表单（腾讯问卷等） | **不能**：无法实现 DCE 的左右随机化、平衡分配、模拟弹窗与作答计时 | ❌ |
| Google Sheet / Airtable API | 技术上可行，但需把密钥放服务端（等于仍要写接口），且导出与分析不如 SQL 灵活 | ⚪ 备选 |
| Netlify Forms | 只能收集普通表单字段，装不下嵌套的 DCE 结构化数据 | ❌ |

**"直接导出 CSV"其实已经支持**：Supabase 的 Table Editor 每张表都有
"Export → CSV" 按钮，无需写任何代码即可手动下载（见 `docs/DATA_DICTIONARY.md`）。
管理后台的 6 种 CSV 导出是在此之上提供**合并、长表、自动鉴权**的便利版本。

若将来确实想彻底摆脱 Supabase，可行路径是"自建极简接口 + CSV 文件落盘"，
但那需要一台常驻服务器或对象存储，成本高于 Supabase Free，且要自己承担
备份与权限，对本科项目并不划算。
